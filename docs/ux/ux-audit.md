# Lotmark console — UI/UX audit

A grounded review of the console's user experience: eleven evaluators read the actual page and component source (and, where useful, drove the live demo), covering each screen group and the cross-cutting dimensions — visual system, accessibility, responsive, interaction states, and information architecture — followed by one synthesis pass. Findings cite `file:line`. The console is already mature (themed light/dark tokens, role-scoped nav with real empty-state handling, a compliance model, some responsive work), so this is about what is genuinely missing or weak, not strawmen.

> Spot-checked and confirmed against the code: the authorised→released **lot release has no console UI** (`POST /projects/:id/release-lot` exists in the API, no web call); the **step-up ceremony is a guaranteed two-attempt flow**; the **audit ledger is capped at 200 with no load-older**; the **catalogue quantity is not clamped to stock**.

## Cross-cutting themes

- **Silent failure & state ambiguity** — Across ProjectDetail, Operations, the audit verdict, People and CAPA, the console cannot tell the user apart three states — loading, failed-to-load, and genuinely empty. A failed /ops fetch renders as 'all healthy', a failed studies query renders as 'No studies yet', and read errors blank whole screens with a raw message and no retry. For an auditable record this is the sharpest defect: absence of a signal reads as absence of the thing.
- **Accessibility is unwired end-to-end** — Zero aria-live/role=alert/aria-invalid anywhere: flashes, auth errors, step-up failures, the audit chain verdict and the global job-health banner are all silent to screen readers. Layered on top: mouse-only project rows, no skip link, non-focusable <main>, no focus move on SPA view change, form errors not tied to their fields, and duplicate h1s in modals. A multi-role regulated tool must be operable by every role.
- **Errors and confirmations in the wrong place** — Mutation failures render on the page body behind the open modal (ProjectDetail signing, every People dialog), so users click a greyed action repeatedly with no visible reason. Conversely, genuinely destructive acts (Discard draft, Deactivate/Revoke, remove a state and its transitions) fire on one click with no confirmation and — unlike the grant flow — capture no reason for the ledger.
- **Feedback that never resolves** — Success flashes are set but essentially never cleared, never auto-dismiss and mostly can't be dismissed, so stale green confirmations accumulate; meanwhile equally-weighty actions (closing a CAPA, creating a study) give no confirmation at all. Loading is inert 'Loading…' text and a .spinner that doesn't spin. There is no shared toast/flash primitive despite ten call sites re-declaring one.
- **Data the system already holds but never shows** — tracking_reference, order currency, dispatch/delivery dates, assigned_by/authorised_by provenance, picklist sortOrder, and per-version config diffs are all in the payload yet dropped in the view — costing the buyer a trackable shipment, hiding the four-eyes provenance the SoD rule depends on, and preventing 'what did version 5 change'.
- **Dead-clicks: unenforced permissions and rules** — Release-chain buttons (Sign, Assign, Authorise, Issue) render unconditionally, so narrow producer roles open the signing ceremony only to be denied server-side; Authorise is offered to the very person the four-eyes rule forbids; quantity exceeds stock; password submits below the stated 12-char minimum. The client knows each rule but ships the predictably-rejected action anyway.
- **No cross-surface wayfinding or attention model** — Every producer lands on a raw table; there is no overview of pending work, no 'what's waiting on me' inbox, no global search/jump-to-code, and a flat 12-item nav with no grouping or overflow. Work is routed between people and teams but is only discoverable by opening each section and hunting.
- **Missing search, filter and sort on the record screens** — The audit ledger (silently capped at 200), CAPA register (not urgency-sorted, KPI tiles inert), Conformance (can't isolate the gaps it exists to show) and Projects all render flat unfilterable lists — the reviewer's core job of isolating DENY/SECURITY, overdue-Critical, or non-enforced clauses is eyeball-scanning.
- **No design-token foundation** — Colors are tokenized but type, spacing, radii and weight are ad hoc: base h2 is overridden with inline fontSize:15 fourteen times, marginTop:13 reimplements the sibling-card rule fourteen times, four near-identical radii and five hand-picked font-weights coexist, and the wordmark is copy-pasted magic numbers. New components have no canonical value to reach for.
- **Low-code designers can't reorder or validate** — The Flow guard condition is a raw hand-typed DSL validated only on a different screen at publish; layouts and picklists can only append/delete with no reorder; the field Order input stays live even when a layout overrides it; role-scoped layouts exist in the model but not the editor. The designers stop short of basic authoring expectations.
- **Mobile is unfinished on the core surfaces** — The phone header starves nav to ~58px behind identity text and utility buttons, primary row actions are 29px (below the 44px touch target), the audit ledger's fixed grid overflows sideways, off-screen nav sections have no scroll affordance, and wide tables push the action into an off-screen last column.

## Prioritized top ten

1. Add 'Release a lot' to the console — the product's core step (authorised value → released lot + certificate) is currently reachable only by curl
2. Auto-complete the signature after step-up instead of discarding the pending target, ending the guaranteed two-attempt flow on the platform's most important compliance action
3. Distinguish loading / error / empty across ProjectDetail, Operations and the list screens — stop failed and in-flight loads reading as 'healthy' or 'nothing exists' in an auditable system
4. Surface every mutation error where the user is looking: thread act errors into the open signing and People dialogs instead of rendering them behind the modal
5. Ship a shared live-region + focus foundation (role=alert/status, focus-on-view-change, field aria wiring) so the multi-role console is operable by screen-reader and keyboard users
6. Confirm and capture a ledgered reason on every destructive act — Discard draft, Deactivate/Revoke, state removal — matching the grant ceremony
7. Permission-gate the release-chain buttons and surface the four-eyes provenance, eliminating dead-clicks into server denials
8. Add a landing overview / 'what needs my attention' home plus a per-user assignments inbox so pending cross-surface work is visible without hunting
9. Give the audit ledger, CAPA register, Conformance and Projects real filter/search/sort (and honest '200 of N' bounds with load-older) so reviewers can isolate the findings
10. Replace the never-clearing per-screen flashes with one transient, dismissible, auto-clearing toast fired on every state-changing success

## High-impact improvements

- **[M] Auto-complete the signature after step-up instead of discarding the pending target.** Signing is the platform's single most important compliance interaction, and today every first signature in a session is a guaranteed two-attempt flow: the pending action is cleared on step_up_required, so after the ceremony succeeds the user must re-locate the row and click Sign again. Stash the pending act and re-invoke the mutation in onUnlocked so it completes in one pass with a real 'signed and recorded in the ledger' confirmation.
- **[M] Distinguish loading, error and empty across the data screens.** ProjectDetail (the busiest screen) reads four queries but never checks isLoading/isError, so a slow or failed load is indistinguishable from an empty project — the exact confusion CertificatePanel works hard to avoid, made on the core release-chain data. Add per-section skeleton/spinner, an error note with retry(refetch), and only show the empty prose after a successful empty result. Extends to Capa/Projects load failures that currently blank the whole screen with a raw error and no retry.
- **[M] Build a shared live-region + focus foundation for accessibility.** One Flash/Alert primitive carrying role=status / role=alert covers ~all announcement gaps at once; pair it with focus-move on SPA view change (focus the new h1, set document.title per surface), aria-invalid + aria-describedby wiring in the shared Field, and demoting modal h1s to h2. Turns a regulated multi-role console from inaccessible to operable across the board.
- **[M] Introduce a transient, dismissible, auto-clearing flash/toast system.** Ten screens re-declare a flash that is set on success but essentially never cleared, so stale green boxes accumulate through unrelated later actions; other equally-weighty actions (CAPA close, study create) confirm nothing. Lift into one Flash/Toast with dismiss + auto-timeout + clear-on-next-mutation, and let child dialogs report success up via onDone(message).
- **[M] Confirm and capture a reason on every destructive act.** Deactivate and Revoke fire on one click and record the removal of authority with less justification than granting it (grant requires a mandatory ledgered reason); removing a workflow state silently drops all its transitions. Route these through a confirm Dialog that names the consequence, captures a required reason into the ledger, and disables on isPending — matching the grant ceremony and the app's auditability story.
- **[M] Permission-gate the release-chain buttons and surface SoD provenance.** Sign/Assign/Authorise/Issue render unconditionally, so a Technical Manager sees Sign, a Production Lead sees Authorise — each a dead-click into a server denial, the opposite of the app's 'you can open nothing' honesty. Thread the held flags down (matching canReissue) and, for four-eyes, surface assigned_by/authorised_by and disable Authorise for the assigner with an explaining title.
- **[M] Give the audit ledger and CAPA register real filtering and honest bounds.** The reviewer's job is isolating DENY/SECURITY events or an overdue-Critical, yet both are flat lists — the ledger silently capped at 200 with no 'showing latest N of M' and no path to older entries (a trust defect for an append-only record), and CAPA sorted by raise date with inert KPI tiles. Add client-side text+KIND filters and a before-cursor 'load older' on audit; overdue-first/severity sort and clickable KPI filters on CAPA.
- **[M] Group and overflow the flat 12-item producer nav.** A full producer sees 12 peer buttons in one strip spanning three distinct jobs (work / records / admin-design), with no grouping and only a sideways-scrolling strip on mobile that hides items with no affordance. Add a group field to the Surface table and render work inline with records/admin collapsed into labelled menus — preserving the one-row-per-surface model while giving wayfinding structure.
- **[L] Establish a design-token foundation (type, spacing, radii, weight).** Base h2 is overridden with inline fontSize:15 fourteen times and marginTop:13 reimplements the sibling-card rule fourteen times; ten font sizes several a half-pixel apart, four near-identical radii and five hand-picked weights coexist. A --fs/--space/--radius/--w token set plus .card-title, a stack utility and a .wordmark class removes dozens of inline overrides and gives every new component a canonical value.
- **[L] Validate Flow guard conditions inside the dialog.** The single least 'low-code' surface: guards are raw hand-typed DSL (record.severity != …) with no field picker and no check until a generic banner after save or refusal at publish on a different screen. Parse client-side against GUARD_FACTS + the entity's custom-field keys and show an inline error on unknown references, plus clickable fact chips so authors insert valid names.

## New features

- **[L] Release a lot from the console.** After signing three studies and authorising a value, the single most important step of the whole product — turning that value into a released lot with a certificate — is reachable only by curl; the server exposes POST /release-lot but no UI does. Needs a dedicated dialog (meaning, expiryDate, stockUnits, unitPriceMinor, reason) gated on lot:release and routed through the existing StepUp flow. The biggest functional gap in the audit.
- **[L] A landing overview / 'what needs my attention' home.** Every producer lands on a raw table; the domain is full of cross-surface handoffs (values awaiting authorisation, studies awaiting signature, lots without certificates, open CAPAs, orders to dispatch) invisible until each section is opened. A default Home surface of counting, deep-linking cards turns the console from tables-you-must-remember-to-check into a task-driven home.
- **[L] A personal assignments inbox.** Work is routed to specific people and teams (CAPA assigned to a section, a value only authorisable by someone other than the assigner, studies awaiting a signer) but nothing answers 'what is specifically waiting on me' — no inbox, badge or 'assigned to me' view exists. Distinct from the overview: this is the per-user work queue with a header count.
- **[L] Global search / jump-to-code command palette.** Everything is identified by human-facing codes (project, lot, certificate, study, CAPA) that people cite in CAPAs, emails and audits, yet there is no way to jump to an entity by code — the only path is scanning the Projects table and drilling down. A header Cmd-K that resolves a code/material across entities and navigates straight there.
- **[L] Per-CAPA transition history timeline.** Every CAPA move already records its reason to the ledger (the ISO 17034 7.11 requirement), but the card shows only current root_cause and corrective_action — a reviewer can't see how it reached its state without leaving to scan the ledger. Expose a collapsible timeline of transitions with reason, actor and timestamp beneath the card.
- **[M] Team membership management.** Teams own records and scope role grants, and the Directory payload already carries the full memberships array the page fetches but never uses — yet an admin can create a team and scope roles to it but cannot put anyone in it or see who is in it. Make the member count open an add/remove roster.
- **[M] 'Expiring soon' competence signal.** The competence chip is binary valid/expired, so a competence lapsing tomorrow looks identical to one valid for a year — the exact silent lapse the page's own header warns bites a signer the day after. Add an amber 'expiring soon' state and a roll-up of who is about to lose authority, turning the lapse into an advance signal.
- **[M] Role-scoped layouts in the Form designer.** LayoutPayload carries roles:string[] and the runtime resolves per record type, but the editor hard-codes roles:[] and never exposes it — a capability present everywhere except the screen meant to author it. Add a role multiselect (or drop the field so the model stops advertising a feature the product can't deliver).
- **[M] Per-version config change diff in history.** The screen exists to answer 'under what rules was this certificate issued, years later', but the before/after change list is computed only for the open draft in the publish dialog and discarded once published, so version history can't answer 'what did version 5 change'. Persist and show each version's own diff.
- **[M] Overlay elevation and reorder controls in the designers.** Two smaller-but-genuine additions: a single --shadow-overlay so modals stop floating flat on the dimmed backdrop separated only by a 1px line, and move-up/down (or drag) on layout fields/sections and picklist values so assembling anything beyond a trivial layout stops requiring delete-and-re-place.

### Auth & onboarding

- **Step-up ceremony forces a second click and discards the pending signing target** · _high_ · I/M
  - Problem: Signing any act (sign study, assign, authorise, reissue, withdraw, config change) fires the mutation, the server returns step_up_required, and onError immediately clears the pending action (setPending(null) in ProjectDetail; setStepUpFor in CertificatePanel/Configuration) BEFORE opening the StepUp ceremony. After the user supplies password + code and the ceremony succeeds, onUnlocked only shows a flash: 'Signing session open. Try the action again.' The original SignAction dialog is gone and the pending target is lost, so the user must re-locate the row, re-open the dialog and click Sign a second time. Every first signature in a session is a guaranteed two-attempt flow. The ceremony already collected everything needed to complete the act; making the user manually re-trigger it is pure friction on the platform's single most important compliance interaction.
  - Fix: Stash the pending action (p + meaning + reason) instead of discarding it on step_up_required, and in onUnlocked re-invoke the same mutation automatically so the signature completes in one pass. In ProjectDetail keep `pending` set (or copy it to a ref) and call act.mutate with the stored args after unlock; in CertificatePanel re-run reissue/withdraw; in Configuration re-run the stashed act. Replace the 'Try the action again' flash with a real completion ('… signed and recorded in the ledger.'). Fall back to the current retry prompt only if the retried call itself fails.
  - `apps/web/src/pages/ProjectDetail.tsx:88, apps/web/src/pages/ProjectDetail.tsx:359, apps/web/src/components/CertificatePanel.tsx:82, apps/web/src/pages/Configuration.tsx:69, apps/web/src/components/StepUp.tsx:38`
- **No show/hide toggle on any password field, against a self-acknowledged lockout risk** · _medium_ · I/M
  - Problem: Every password input is masked with no reveal control: sign-in (SignIn.tsx:64), the step-up ceremony (StepUp.tsx:63), and all three fields of the forced/voluntary password change (ChangePassword.tsx:98,105,111). ChangePassword's own header comment states a typo here 'is a lockout that only an administrator can undo,' and the forced-change screen is the first-login gate for new accounts (newuser@). Requiring a 12+ character new password twice, blind, is exactly where mismatches and silent typos happen — the confirm field catches mismatches but not a value the user simply can't verify before committing.
  - Fix: Add a reveal toggle (eye button inside the field, type flips password/text) to at minimum the two new-password fields on ChangePassword and the step-up password, ideally sign-in too. This directly mitigates the lockout risk the code already worries about and is standard for onboarding password creation.
  - `apps/web/src/pages/ChangePassword.tsx:105, apps/web/src/pages/ChangePassword.tsx:111, apps/web/src/components/StepUp.tsx:63, apps/web/src/pages/SignIn.tsx:64`
- **Forced password change enables submit below the stated minimum and wipes current password on rejection** · _medium_ · I/S
  - Problem: The New password hint says 'at least 12 characters' (ChangePassword.tsx:103) but the submit gate only checks `newPassword.length > 0` (line 55). A user can submit a too-short password, eat a server round-trip rejection, and — because onError calls setCurrent('') (line 71) — have their Current password field silently cleared, forcing them to retype it while the actual problem was the new one. The client already knows the 12-char rule (it prints it) yet doesn't enforce it, turning a locally-preventable mistake into a server round trip plus a re-entry. On the forced-change onboarding gate this is the worst place for that loop.
  - Fix: Enforce the known length rule client-side: include `newPassword.length >= 12` in `submittable`, and surface a live inline hint on the New password field (e.g. neutral until 12 chars, then satisfied) mirroring the mismatch handling already on the confirm field. Keep the server as the authority but stop shipping a submit that the server will predictably reject.
  - `apps/web/src/pages/ChangePassword.tsx:54, apps/web/src/pages/ChangePassword.tsx:71, apps/web/src/pages/ChangePassword.tsx:103`
- **Sign-out can fail silently, leaving the user appearing signed in with no feedback** · _medium_ · I/S
  - Problem: signOut in App.tsx (73-97) awaits POST /auth/sign-out then reloads, with no try/catch and no busy state. If the POST rejects (network drop, transient 5xx), the reload on line 96 never runs, the promise rejects unhandled, and the console keeps rendering the current user's shell — the header 'Sign out' button (line 170) shows no spinner, no error, nothing. In a regulated console a user who clicks Sign out on a shared workstation and walks away, believing the session ended when it did not, is a real trust/compliance gap. The success path is carefully handled (the reload comment explains why); the failure path is unhandled.
  - Fix: Wrap the POST in try/catch, add a busy/disabled state to the Sign out button, and on failure show an inline error ('Could not sign out — check your connection and try again'). Optionally still force the reload in a finally so the client-side session is dropped even if the server call couldn't be confirmed, while telling the user it may not have reached the server.
  - `apps/web/src/App.tsx:73, apps/web/src/App.tsx:170`
- **Authentication error messages are never announced to assistive technology** · _medium_ · I/S
  - Problem: Across the entire auth flow, failure feedback is rendered as a static `<div className="note deny">` with no aria-live region, no role=alert, and inputs carry no aria-invalid / aria-describedby (grep for aria-live/role=alert/aria-invalid/aria-describedby returns nothing in the whole src tree). A screen-reader user who enters a wrong password (SignIn.tsx:67), a bad step-up code (StepUp.tsx:76), or hits a password-change error (ChangePassword.tsx:115) gets no announcement that the attempt failed — the only signal is text that silently appears. The Field component even renders its error as a bare span (Dialog.tsx:44) with no programmatic link to the input. Auth is the one place where every user, including AT users, must know an attempt failed.
  - Fix: Give the inline error containers role="alert" (or wrap in an aria-live="assertive" region) so new errors are announced, set aria-invalid on the offending inputs, and link Field errors via aria-describedby to their input in Dialog.tsx. Small, mechanical, and applies uniformly to SignIn, StepUp, ChangePassword, and the Field helper.
  - `apps/web/src/pages/SignIn.tsx:67, apps/web/src/components/StepUp.tsx:76, apps/web/src/pages/ChangePassword.tsx:115, apps/web/src/components/Dialog.tsx:44`
- **Second-factor lockout gives no recovery path and drives stage reset off brittle string matching** · _low_ · I/M
  - Problem: The second-factor screen shows 'Attempt {attempt} of 3' (SignIn.tsx:76) but offers no recovery affordance — no 'lost your authenticator / use a backup code' path and no 'contact your administrator' guidance for someone who cannot produce a code. When the server exhausts attempts, the client decides to bounce back to credentials purely by substring-matching the server's prose: `if (detail.includes('Sign in again'))` (line 39). That couples control flow to exact server copy — a wording change silently breaks the reset — and the client also never caps attempts itself (it will happily render 'Attempt 4 of 3'), trusting the server's message text to drive the transition.
  - Fix: Drive the stage reset off a structured signal (a problem `type`/code such as second_factor_exhausted) rather than detail.includes(), and add an explicit recovery affordance on the 2FA screen — at minimum a 'Can't access your authenticator? Contact your tenant administrator' line, and a hook for backup codes if the backend supports them. Cap the attempt display client-side so it never exceeds the stated maximum.
  - `apps/web/src/pages/SignIn.tsx:29, apps/web/src/pages/SignIn.tsx:39, apps/web/src/pages/SignIn.tsx:76`

- **A failed sign/assign/authorise/issue shows nothing in the open dialog** · _high_ · I/S
  - Problem: When act fails for any reason other than step-up (e.g. a 422 'no authorised value', competence lapsed, SoD block), onError sets a page-level error but never closes the dialog: setPending(null) is only called on the step-up branch (ProjectDetail.tsx:92), not on the general branch (ProjectDetail.tsx:96).
